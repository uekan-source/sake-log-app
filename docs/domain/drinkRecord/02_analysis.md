## ボスの指摘とその検証（2026-08-20）

**指摘：** プロンプトが大きくなるから、お酒の種類は絞った方がいい。

**検証：** プロンプトは種類数に比例して育つが、3 種で千〜二千トークン程度と誤差。さらに「種類判定 → 種類別の抽出」の 2 段構成にすれば種類が増えてもプロンプトは一定（区分値が隣のフィールドの読み方を決める、の AI 呼び出し版）。**絞るべき本当の理由はプロンプトではなく設計量**（種類ごとに属性・確認画面・データ例・検証が増える）。

**採用：** 深く属性を持つ種類はワインと日本酒の 2 種に絞る（発注者の判断。よく写真を撮るのがこの 2 種のため）。ウイスキーは今回やらない → 2 周目の追加機能候補。種類を後から 1 つ足して設計が壊れなければ、切り分けが正しかった検証になる。

## 論点の種（設計段階で扱う。まだ結論を出さない）

- **種類は enum、品種・酒米はテーブルか文字列。** `design_lessons.md`「enum にするかテーブルにするか」の基準で確認済み：種類は増えたら属性と画面のコードを書く（エンジニアが増やす）→ enum。品種は増えてもコードが変わらず、AI とユーザーが増やす開集合 → enum 禁止。品種をマスタにすると表記ゆれ（ピノノワール／ピノ・ノワール）を引き受ける → 付録B 候補
- **AI の推定値とユーザーの確定値の区別。** 写真 → 解析中 → 推定（未確定）→ 確認・修正 → 確定、の状態を持つか。AI が外れても手入力に落ちて成立する構造（カバレッジの穴で死なない）
- **銘柄（マスタ）と「飲んだ記録」（体験）の分離。** 同じ銘柄を別の日に飲む。ワインはさらにヴィンテージ（同じ銘柄の別の年）をどこに置くかがある
- **「調べただけ」と「飲んだ記録」の分離。** メニューで照会して頼まなかった酒を保存するか
- **AI は外部サービスのアクター。** 所持物なし、結果を写す列が要る（レセコンと同じ型）
- **ログインの意味づけ。** 複数ユーザー前提にするなら userId が全テーブルに乗る境界の鍵になる（shopId の教訓）。ただし発注者は「どちらでも」なので、意味の持たせ方から設計判断
- **目的が「貯める」より「覚える・詳しくなる」に寄っている。** ただ保存できても見返さなければゴールに届かない。振り返りの形は要求にまだ無い → 質問リスト候補の領域

## Q1〜Q8 の回答で分かったこと（2026-08-20 追記）

- **Q1 の起案は外れていた。** 「AI の説明 vs 自分の感想」の区別を提案したが、発注者の意図は「**味わい**（商品ごとの個体差。同じメルローでも軽い・重い）＋**豆知識**（覚える助けになる背景話）」だった。どちらも AI が調べる側の情報。**自分の感想を持つかは未確定のまま残った → Q10 を追加**。外した理由：目的（覚える・詳しくなる）より先に項目の形を聞いた
- **「誰と」は記録しない（Q2）。** アクターシートに置いた「同席者（彼女など）＝記録の属性」は**属性としても消えた**。段階 1 の所持物表のその行は撤回
- **写真の取り込みは一度きりの初期移行ではなく継続機能（Q6）。** 「撮ったのにアップロードしなかった写真を後からあげる」が通常の使い方に含まれる。はみ出し表で 5 分迷った「機能か移行か」は**機能**で確定。まとめて取り込み → 後から順に確認、なので**未確認の推定が溜まっている状態**が普通に存在する → 状態設計に効く
- **応答時間の要求が出た（Q4）。** 利用イメージは「注文 → ボトルの写真を撮る → **飲みながら画面をチェック**」。推定結果は飲んでいる間（数分以内）に見たい。確認・修正は後でよい。段階 3 のフローはこの場面を軸に書く
- 「気になる」（調べたが飲んでいない）は残す（Q3）。論点の種「調べただけと飲んだ記録の分離」は要求として確定
- 残り：**Q9（保存期間）未回答、Q10（自分の感想）新規**

## 実現方式のメモ（設計の外だが記録しておく）

- 知識源は差し替え可能な外部サービスとして扱う。実装候補は Gemini API 無料枠（2026-08 時点で 1 日 1,500 回）から始め、精度不足なら検索 API（Brave / Tavily 等の無料枠）を直列に足す 2 段構成
- デモは AI 部分をモック（固定 JSON）にしても「推定 → 確認 → 確定」の流れは見せられる
- コストは月数十円オーダー。題材選定の変数にしない、と合意済み
- **知識源が探してきた画像の保存は権利面がグレー**（他人の商品写真）。個人利用の範囲では実害は小さいが、公開デプロイするなら画像 URL の参照に留めるか自分の写真だけにする選択肢を残す。実装時に判断
- **ログインなしの照会は API コストが不特定者に開放される**形になる。公開デプロイ時はレート制限などの乱用対策が要る。実装時の課題
